### 深度拆解 + 避坑指南

#### 1. Continuous Delivery vs Continuous Deployment（一字之差，天壤之别）
| 术语 | 定义 | 人工干预 |
| :--- | :--- | :--- |
| **Continuous Delivery** | 代码始终处于可部署状态，但发布需要手动触发 | 需要人工批准 |
| **Continuous Deployment** | 每次通过测试的变更都自动部署到生产 | 零人工干预 |

- **技术场景**：*We use continuous delivery to have a final approval step, but the pipeline is fully automated for continuous deployment to staging.*
- **解释**：Continuous Delivery强调"随时可发布"，Continuous Deployment强调"自动发布"。

#### 2. Canary vs Blue-Green vs Rolling（三种发布策略）
| 策略 | 部署过程 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **Blue-Green** | 两套环境互换 | 切换快，回滚秒级 | 需要双倍资源 |
| **Canary** | 逐步扩量 | 风险低，可测试真实流量 | 流程较慢 |
| **Rolling** | 滚动替换 | 资源利用率高 | 回滚较慢，停机风险 |

- **技术场景**：*We use canary deployment for risky features and blue-green for critical services.*
- **解释**：Canary适合灰度验证新功能，Blue-Green适合核心服务快速切换。

#### 3. Staging vs Pre-Production vs Development vs Production（环境对比）
| 环境 | 用途 | 数据 |
| :--- | :--- | :--- |
| **Development** | 开发自测 | 模拟数据 |
| **Integration** | 联调测试 | 模拟数据 |
| **Testing** | QA测试 | 模拟数据 |
| **Staging** | 最终验证 | 脱敏的镜像数据 |
| **Pre-Production** | 上线前最后检查 | 生产数据副本 |
| **Production** | 实际运行 | 真实数据 |

- **技术场景**：*We test on staging with production-like data before deploying to production.*
- **解释**：每个环境的目标不同，Staging是"最后一公里"的预演。

#### 4. Liveness Probe vs Readiness Probe（两种探针的差异）
| 探针 | 检测内容 | 失败后 |
| :--- | :--- | :--- |
| **Liveness Probe** | 容器是否仍然存活 | 重启容器 |
| **Readiness Probe** | 容器是否可以接受流量 | 从负载均衡中移除 |

- **技术场景**：*We use liveness probe to restart hung pods and readiness probe to avoid sending traffic to starting pods.*
- **解释**：Liveness决定"生与死"，Readiness决定"接不接活"。


### 快速决策流（0.5 秒选择）

你在规划和执行发布时——

- **选择发布策略**？
  - 核心服务，需要秒级回滚 → **Blue-Green**
  - 高风险功能，需要逐步验证 → **Canary**
  - 资源有限，平滑升级即可 → **Rolling**
  - 对比两个版本的业务效果 → **A/B Testing**

- **决定何时发布**？
  - 常规版本 → **预发布窗口（如每周二 14:00）**
  - 非紧急修复 → 跟随下一个 **Release Plan**
  - 线上紧急事故 → **Hotfix**（事后补测试）

- **验证部署成功**？
  - 基础检查 → 观察 **Health Check** / **Readiness Probe** 状态
  - 功能检查 → 运行 **Smoke Test**（冒烟测试）
  - 业务检查 → 观察核心 **SLO**（如错误率、延迟）不超过阈值

- **部署过程中出现故障**？
  - 如果故障范围小（Canary 阶段）→ 立即暂停扩展，终止 **Canary**
  - 如果所有实例都异常 → 立即执行 **Rollback**
  - 如果回滚也慢 → 切换到已就绪的 **Blue** 环境（**Fallback**）

- **监控线上服务运行状况**？
  - 查看实时指标 → **Dashboard**（如 Grafana）
  - 查看错误日志 → **Logging**（如 ELK / Loki）
  - 查看请求链路 → **Tracing**（如 Jaeger / Zipkin）
  - 收到告警 → 根据 **Alert** 进入 **On-Call** 流程


### 技术场景组合示例（完整的发布流程描述）

> *We follow a blue-green deployment strategy for all production releases. The CI/CD pipeline builds a Docker image and pushes it to the container registry. The deployment is first rolled out to the staging environment for integration testing and UAT. After approval, the new version is deployed to the green environment while the blue environment continues to serve production traffic. We run health checks and smoke tests in the green environment. Once all tests pass, we switch the load balancer to route traffic to the green environment, achieving zero-downtime deployment. If any issues are detected, we execute an automatic rollback to the blue environment. Throughout the process, we monitor SLIs like latency and error rate to ensure we meet our SLOs. We use feature flags to control feature rollout and implement canary deployment for high-risk changes. All releases are tagged with semantic versioning in Git, and release notes are generated automatically.*

> （我们对所有生产发布采用蓝绿部署策略。CI/CD 流水线构建 Docker 镜像并推送到容器注册表。部署首先推送到预发布环境进行集成测试和用户验收测试。批准后，新版本部署到绿色环境，而蓝色环境继续为生产流量提供服务。我们在绿色环境中运行健康检查和冒烟测试。所有测试通过后，我们切换负载均衡器将流量路由到绿色环境，实现零停机部署。如果检测到任何问题，我们执行自动回滚到蓝色环境。在整个过程中，我们监控 SLI，如延迟和错误率，以确保满足 SLO。我们使用功能开关控制功能发布，并对高风险变更实施金丝雀发布。所有发布都在 Git 中使用语义化版本打标签，并自动生成发布说明。）
