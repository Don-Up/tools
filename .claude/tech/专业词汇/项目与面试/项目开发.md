### 深度拆解 + 避坑指南

#### 1. Sprint vs Iteration（核心区别）
| 术语 | 定义 | 适用场景 |
| :--- | :--- | :--- |
| **Sprint** | Scrum 中的固定时长迭代 | Scrum 框架中的迭代 |
| **Iteration** | 通用术语 | 任何迭代式开发方法 |

- **技术场景**：*We have 2-week sprints in our Scrum process.*
- **解释**：Sprint是Scrum专属术语，其他敏捷框架中用Iteration更通用。

#### 2. Velocity vs Capacity（互补而非互斥）
| 术语 | 定义 | 用途 |
| :--- | :--- | :--- |
| **Velocity** | 历史平均交付速率 | 用于预测未来Sprint可完成的故事点数 |
| **Capacity** | 团队实际可用时间 | 用于估算当前Sprint的可用人天 |

- **技术场景**：*Our velocity is 30 points, but this sprint's capacity is lower due to holidays.*
- **解释**：Velocity是历史指标，Capacity是当前能力。

#### 3. Story Points vs Hours（相对估算 vs 绝对估算）
| 估算方式 | 优点 | 缺点 |
| :--- | :--- | :--- |
| **Story Points** | 相对估算，不易受个人速度影响 | 初学者难以理解 |
| **Hours** | 直观易懂 | 受个人速度影响大 |

- **技术场景**：*We use story points for estimation to keep the process simple.*
- **解释**：Story Points 估算复杂度，Hours 估算时间。

#### 4. Backlog Refinement vs Sprint Planning（两个阶段的区别）
| 会议 | 目的 | 时间 |
| :--- | :--- | :--- |
| **Backlog Refinement** | 为待办事项补充细节、估算、重新排序 | Sprint期间，非正式 |
| **Sprint Planning** | 承诺当前Sprint要完成的工作 | Sprint开始时，正式 |

- **技术场景**：*We refine the backlog before sprint planning to ensure stories are ready.*
- **解释**：Backlog Refinement做准备工作，Sprint Planning做承诺决策。


### 快速决策流（0.5 秒选择）

你要进行项目管理活动时——

- **进行估算**？
  - 如果团队经验丰富且喜欢快速估算 → 用 **Story Points + Planning Poker**
  - 如果团队是新手或习惯看绝对时间 → 用 **T-shirt Sizing** 或 **Hours**
  - 如果是在会议上做高层面板估算 → 用 **T-shirt Sizing**

- **在 Sprint 中进度落后时优先处理什么**？
  - 如果剩余工作量巨大（超过 Sprint 容量）→ 与 PO 协商 **Scope**（范围）**缩减**，砍掉低优先级 Story
  - 如果问题是外部依赖等待 → 向 **Scrum Master** 报告 **Impediment**
  - 如果是常规落后但可追赶 → 每日站会上 **Swarm**（集结攻坚），多人集中攻克剩余任务

- **评估团队状况**？
  - 如果想知道“未来能交付多少” → 看 **Velocity**（速度）
  - 如果想知道“当前流程在哪里卡住” → 看 **Cumulative Flow Diagram**（累积流程图）或 **Cycle Time**（周期时间）
  - 如果想知道“团队能释放多少人手做新需求” → 看 **WIP Limit**（在制品限制）

- **处理重大事故（Post-Mortem 复盘）**？
  - 找直接原因 → 进行 **Root Cause Analysis**（根本原因分析）
  - 防止再次发生 → 落地 **Action Items**（改进措施）并跟踪 **Mitigation**（缓解计划）
  - 建立知识库 → 归档 **Post-Mortem** 文档

- **发布策略选择**？
  - 零停机部署 → 用 **Blue-Green Deployment**
  - 风险最小化试点 → 用 **Canary Release**
  - 动态控制功能上线 → 用 **Feature Flag**
  - 紧急修复 → 用 **Hotfix**


### 技术场景组合示例（完整的敏捷开发流程描述）

> *We follow an Agile Scrum framework with 2-week sprints. At the sprint planning meeting, the Product Owner presents the highest-priority user stories from the product backlog. The team estimates each story using Planning Poker and Fibonacci sequence points, then commits to a sprint goal based on the team's historical velocity. Each story has clear acceptance criteria and a Definition of Done that includes code review, testing, and documentation. We hold a daily stand-up every morning to sync on progress and identify any blockers. Throughout the sprint, we use a Kanban board to visualize the workflow and track work items. At the end of the sprint, we demo completed features at the sprint review, then hold a sprint retrospective to discuss what went well and what needs improvement. We track our progress using a burndown chart and monitor our cycle time to identify bottlenecks in the workflow.*

> （我们遵循敏捷 Scrum 框架，采用 2 周的冲刺周期。在冲刺规划会上，产品负责人从产品待办列表中展示最高优先级的用户故事。团队使用计划扑克和斐波那契数列点数进行估算，然后基于团队的历史速度承诺冲刺目标。每个故事都有明确的验收标准和完成的定义，包括代码审查、测试和文档。我们每天早上举行每日站会，同步进度并识别任何阻碍。在冲刺过程中，我们使用看板来可视化工作流并跟踪工作项。冲刺结束时，我们在冲刺评审会上演示已完成的功能，然后举行冲刺回顾会，讨论哪些方面做得好，哪些方面需要改进。我们使用燃尽图跟踪进度，并监控周期时间以识别工作流中的瓶颈。）
