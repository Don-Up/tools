### 深度拆解 + 避坑指南

#### 1. `@MessagePattern()` vs `@EventPattern()`（NestJS 核心区别）
| 装饰器 | 需要响应 | 适用场景 |
| :--- | :--- | :--- |
| **`@MessagePattern()`** | 是（需要 `Observable` 或 `Promise`） | 命令、RPC 调用 |
| **`@EventPattern()`** | 否（不返回响应） | 事件通知、异步处理 |

- **技术场景**：*Use `@MessagePattern()` for request-response commands and `@EventPattern()` for events that don't require a response.*

#### 2. TCP vs Redis vs Kafka（NestJS 传输层选择）
| 传输层 | 适用场景 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **TCP** | 内部服务通信（高性能） | 低延迟，简单 | 不支持持久化 |
| **Redis** | 发布/订阅模式 | 轻量级，快速 | 消息易丢失 |
| **Kafka** | 事件流、高吞吐量 | 持久化，高可靠性 | 运维复杂 |
| **gRPC** | 跨语言高性能 RPC | 多语言支持，高性能 | 需要定义 `.proto` |

- **技术场景**：*Use TCP for fast internal communication, Redis for simple pub/sub, and Kafka for event streaming.*

#### 3. Orchestration vs Choreography（Saga 编排与协同的差异）
| 模式 | 协调方式 | 适用场景 |
| :--- | :--- | :--- |
| **Orchestration** | 中央协调器调用各个服务 | 流程复杂、步骤较多的长事务 |
| **Choreography** | 服务通过事件相互驱动 | 流程简单、各服务独立性强 |

- **技术场景**：*Use orchestration when you have complex business logic and need to centrally manage the flow. Use choreography when you need high decoupling between services.*


### 快速决策流（0.5 秒选择）

你在设计微服务架构（基于 NestJS）时——

- **服务间如何通信**？
  - 需要低延迟内部通信 → NestJS **TCP Transporter**
  - 需要发布/订阅 → NestJS **Redis Transporter**
  - 需要事件流高吞吐 → NestJS **Kafka Transporter**
  - 需要跨语言高性能 RPC → **gRPC**

- **选择消息模式**？
  - 需要返回响应（类似 RPC） → `@MessagePattern()` + `@Payload()`
  - 只需要发送通知，无需响应 → `@EventPattern()`
  - 广播给多个服务 → 使用 **Pub/Sub**
  - 只给一个服务消费 → 使用 **Point-to-Point**

- **处理分布式事务**？
  - 短事务、强一致性 → 尽量用 **Database per Service** + **API Composition**
  - 长事务、最终一致性 → 使用 **Saga Pattern**
  - 需要追踪补偿逻辑 → **Orchestration-Based Saga**（中央协调器）
  - 希望服务之间高度解耦 → **Choreography-Based Saga**（事件驱动）
  - 出现失败需要撤销 → 实现 **Compensating Action**

- **保障可靠性**？
  - 处理临时故障 → 实现 **Retry** + **Exponential Backoff**
  - 防止级联故障 → 使用 **Circuit Breaker**
  - 限流防 overload → 实现 **Rate Limiting**
  - 定义超时防止无限等待 → 设置 **Timeout**

- **实现可观测性**？
  - 追踪跨服务请求链路 → 生成并传递 **Correlation ID**
  - 分析服务间调用耗时 → 启用 **Distributed Tracing**（如 Jaeger）
  - 汇总日志进行搜索分析 → 采用结构化 **Logging**（如 ELK）


### 技术场景组合示例（完整的 NestJS 微服务描述）

> *We are building a **microservices architecture** with **NestJS**. Each service is built as a separate application and communicates via the **TCP transporter**. We use **`@MessagePattern()`** for request-response commands and **`@EventPattern()`** for event notifications. For inter-service communication, we use **ClientProxy** to send messages to other services. The **API Gateway** aggregates responses from multiple services using **API composition**. We follow the **database per service** pattern to ensure loose coupling. For distributed transactions, we use a **saga pattern** with compensation logic. All services register themselves with a **service registry** for **service discovery**. We implement **circuit breakers** and **retries** with **exponential backoff** for resilience. A **correlation ID** is passed through all services for **distributed tracing**. We expose **health check** endpoints for monitoring and use **feature flags** to control feature rollout. The system is deployed using **Docker** and **Kubernetes**.*

> （我们正在使用 **NestJS** 构建一个**微服务架构**。每个服务作为一个独立的应用程序，通过 **TCP 传输层** 进行通信。我们使用 **`@MessagePattern()`** 处理请求-响应命令，使用 **`@EventPattern()`** 处理事件通知。对于服务间通信，我们使用 **ClientProxy** 向其他服务发送消息。**API 网关**通过 **API 组合模式** 聚合来自多个服务的响应。我们遵循 **每服务独享数据库** 模式以确保松耦合。对于分布式事务，我们使用具有补偿逻辑的 **Saga 模式**。所有服务都注册到**服务注册中心**以实现**服务发现**。我们实现了**熔断器**和带有**指数退避**的**重试**机制来保证韧性。所有服务间请求传递 **Correlation ID** 以实现**分布式链路追踪**。我们暴露**健康检查**端点用于监控，并使用**功能开关**控制功能发布。系统使用 **Docker** 和 **Kubernetes** 部署。）
